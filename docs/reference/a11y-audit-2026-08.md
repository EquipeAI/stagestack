# Accessibility audit — 2026-08 (W6)

Target: WCAG 2.2 Level AA. Codebase at `apps/web/src`, branch `develop`.

## What this is, and what it is not

This is a **static code audit**. Every finding below was reached by reading
source — components, CSS, computed token values — not by operating the running
application. Nothing here was verified in a browser.

Specifically **not done, and not claimed**:

- No axe (or any automated scanner) run against a rendered page.
- No manual keyboard pass over a live surface.
- No screen-reader pass (VoiceOver / NVDA / JAWS).
- No real measurement of rendered target sizes, contrast, or reflow at 200%
  zoom — the target-size and contrast verdicts below are computed from token
  values and CSS, which is a sound way to find failures and a weak way to
  confirm passes.

Those three passes belong to the plan's final verification step and remain
outstanding. A fix marked **Fixed** here means the code defect was removed and,
where testable, a regression test exists; it does not mean the result was
observed working.

Two claims in the plan were **confirmed**, not rebuilt:

- `DataTable` rows are focusable and Enter/Space-activated, with a guard so a
  control inside a cell does not double-fire
  (`apps/web/src/ds/components/layout/DataTable.jsx:38-48`), and the horizontal
  scroller is `role="region"` + `tabIndex={0}` + `aria-label` (`:14-18`).
- The agenda has real keyboard placement: a lattice-aware `KeyboardSensor`
  coordinate getter, Space to pick up, Escape to cancel, custom
  `screenReaderInstructions` and hand-written announcements that name the block
  and the target slot in event time
  (`apps/web/src/components/agenda/keyboardDrag.ts`,
  `apps/web/src/components/agenda/AgendaBoard.tsx:171-204`, unit-tested in
  `keyboardDrag.test.ts`).

## 3. Live regions (plan item 4)

`ActionResult` already had `role="status"` + `aria-live="polite"`
(`ds/components/feedback/ActionResult.jsx:65`) — verified, not duplicated. The
gap was everything else: inline errors, pending→done transitions and filter
counts were all silent.

**One mechanism, not per-surface hacks.** `apps/web/src/lib/announce.ts` owns
the app's only pair of live regions — one polite, one assertive — rendered by
`apps/web/src/components/LiveRegion.tsx` and mounted once in
`routes/__root.tsx`. The root, not the toast viewport: every route runs
mutations through `usePending`, and `/invite` has no toasts, so a region living
beside them would have been absent exactly where it was needed.

`usePending` feeds those regions, and takes `{ announce: false }` for a surface
that already announces the same failure itself (an `ActionResult`, a `Field`
error, a hand-rolled `role="alert"`), plus `{ announce: '<action name>' }` for
long work with no visible outcome.

The remaining announcers are all **element-scoped and describe their own
element**, never the same event as another: `ActionResult` (the only other
`aria-live` in the codebase), `Field`'s error span, and the `role="status"`
nodes on the public widgets' result counts, `ProfileCard`'s saved indicator,
`BrandColorField`'s contrast warning, `ReviewQueue`'s progress line and the
two `role="alert"` Callouts. No two of them speak the same sentence — that is
what the `{ announce: false }` census below is for.

## 9. Zoom and narrow width (plan item 9)

Static check only — no browser was opened, so nothing here is a reflow
verdict, only a search for content removed by a media query.

Every `display:none` inside a media query in the DS and in `app.css`:

| Rule | What it hides | Assessment |
|---|---|---|
| `layout.css:32`, `navigation.css:57,94` | `::-webkit-scrollbar` | Cosmetic. The containers stay scrollable |
| `forms.css:52` (`@media (hover:none)`) | The `/`-shortcut `<kbd>` hint in `SearchInput` | A hint about a keyboard, hidden on devices without one. Deliberate; hides no action |
| `navigation.css:45` (`≤860px`) | `.ss-sidebar__head` — the sidebar header slot | **Flagged, not fixed.** The current caller puts only the event name there, which is also the page `<h1>`, so nothing is lost today. But `SidebarNav` takes an arbitrary `header` node, so any *action* placed there would silently vanish on a phone. **W7 owns the mobile drawer** and should either render the header in the drawer or drop the prop |
| `navigation.css:59` (`≤860px`) | `.ss-sidebar__group` — the nav group labels | **Flagged, not fixed.** `display:none` removes them from the accessibility tree too, so below 860px the lifecycle grouping is invisible to everyone. This is precisely the problem **W7's real mobile drawer** exists to solve; the plan already names it |
| `navigation.css:69` (`≤860px`) | The active item's left-edge bar | Fixed above — the replacement is no longer colour-only |

No navigation entry and no action is hidden at any width. The `860px` block in
`app.css:45` only changes `flex-direction`; nothing is hidden there. The public
page, the portal and every widget use flow layout with `flex-wrap` and
percentage widths, with no fixed-width containers that would clip at 200% zoom
— but that is an inspection, not a measurement.
